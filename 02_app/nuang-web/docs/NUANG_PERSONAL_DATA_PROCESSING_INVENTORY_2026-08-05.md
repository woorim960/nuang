## 3. 계정 삭제 전수 대조

1. 서버는 사용자의 account 연결을 확인하고 `profile-avatars`, `feed-media` 소유 객체 경로를 읽는다.
2. Storage 객체를 최대 100개 단위로 먼저 삭제한다. 실패하면 DB 계정 삭제를 시작하지 않는다.
3. `delete_own_nuang_account` RPC는 다중 OAuth canonical account와 연결 Auth 사용자를 계산하고, 기존 identity 감사 기록에서 직접 식별자를 제거한 뒤 `identity.account`와 `auth.users`를 삭제한다. provider subject tombstone은 만들지 않는다.
4. account FK의 `on delete cascade`로 검사·리포트·동의·프로필·게시물·관계·계정 연결 연구 피드백 등을 삭제한다.
5. 성공 후 브라우저 로그아웃과 `nuang*` localStorage, IndexedDB `nuang-local` 삭제를 요청한다.

### 확인된 잔존·실패 위험

- `deleted_auth_identity_tombstone`은 비우고 신규 기록을 중단한다. 삭제 성공 감사에는 계정·Auth 사용자·provider subject·이메일·연락처를 남기지 않고 삭제 건수만 기록한다.
- 관리자·연구 결정·마케팅 캠페인 등 운영 산출물은 운영자 계정 삭제 시 actor FK를 null 처리해 개인 연결을 제거한다. 병합 case는 cascade 삭제한다.
- Storage 삭제 뒤 DB 삭제가 실패하면 계정은 남지만 이미지가 먼저 없어지는 부분 성공 상태가 생길 수 있다. 재시도 outbox 또는 DB 삭제 후 비동기 Storage 정리 모델이 필요하다.
- 브라우저의 계정 삭제 후 로컬 정리는 응답 성공 뒤 실행되므로 탭 종료·브라우저 실패 시 남을 수 있다. 사용자는 사이트 데이터 삭제가 가능해야 하며, 앱도 다음 시작 시 삭제 완료 marker 기반 재정리를 검토해야 한다.
- 공급자 백업과 플랫폼 로그는 애플리케이션 삭제 RPC 범위 밖이다.
