# NUANG 베타 사용자 가치 검증·제품 분석 운영 기획

- 문서 버전: `beta-analytics-v1.0`
- 작성일: 2026-08-05
- 상태: 구현 기준 확정
- 적용 범위: 제품 이용 분석, 사용자 가치 검증, 고객 의견·결과 품질 신호, 운영자 집계 화면
- 제외 범위: 광고 성과, 연령 정책, 법률 문구·법적 근거 판단, 마케팅 캠페인

## 1. 목표와 성공 조건

베타 운영의 목적은 “트래픽이 늘었는가”보다 사용자가 뉴앙의 핵심 가치를 실제로 경험했는지를 빠르게 확인하는 것이다. 분석 수집은 서비스 동작보다 항상 후순위이며, 동의가 없거나 분석 시스템이 고장 나도 검사·결과·함께하기·커뮤니티 기능은 그대로 동작해야 한다.

성공 조건은 다음과 같다.

1. 발견 → 시작 → 완료 → 결과 확인 → 도움 평가 → 공유·비교 → 재방문의 흐름을 동일한 정의로 매주 비교한다.
2. 검사 답변, 결과 본문, 게시글·댓글, 검색어, 방 이름, 닉네임, URL 식별자 같은 내용을 제품 분석 이벤트에 넣지 않는다.
3. 선택 동의와 브라우저의 추적 거부 신호를 우선하고, 수집 실패는 사용자에게 노출하지 않는다.
4. 운영 화면은 개인 단위 탐색이 아닌 최소 집계만 제공한다.
5. 수집 코드가 초기 렌더링·입력 반응·화면 전환을 지연시키지 않는다.

## 2. 현재 구조 조사 결과

### 2.1 이용 분석

- 전역 `ProductAnalyticsBoundary`가 민감·비제품 경로를 제외하고 화면을 `home`, `assessment`, `result`, `community`, `trait_map`, `my`, `together`, `settings`, `other`로 정규화한다.
- 브라우저는 원본 경로·쿼리·결과 ID를 보내지 않고 `screen_view`와 정규화된 영역만 `/api/analytics/events`로 보낸다.
- API는 동일 출처, 엄격한 요청 스키마, 로그인 사용자, 정상 계정, 분석 선택 동의를 모두 통과한 경우에만 저장한다. 실패·비동의·중복은 `204`로 조용히 종료한다.
- `consent.product_analytics_event`는 계정 ID, 이벤트명, 영역, 시각만 저장한다. 5분 내 동일 영역은 DB에서 중복 제거되고 90일 보존 작업이 예약돼 있다.
- 현재 한계는 로그인·동의 사용자 화면 조회만 있어 시작·완료·공유·비교·오류 퍼널을 이벤트만으로 계산할 수 없고, 운영자 전용 분석 화면도 없다는 점이다.

### 2.2 고객 의견과 결과 품질

- `public.product_feedback`은 로그인·비로그인 모두 오류, 사용성, 아이디어 의견을 보낼 수 있다. 본문, 정규화 영역, 앱 내부 source path, locale/timezone/viewport가 저장된다.
- 익명 의견의 요청 지문은 세션 ID·IP·user-agent를 서버 비밀값으로 HMAC 처리하며 원문 IP와 user-agent는 저장하지 않는다.
- `assessment.quality_observation`은 선택 동의가 확인된 계정의 문항 이해·수정·결과 적합도 신호를 저장한다.
- `report.core_result_feedback`은 계정 소유 결과의 문장 버전별 `fit`, `depends`, `not_fit` 응답을 저장한다.
- 관리자 고객 의견 화면은 제품 의견, 검사 품질 신호, 결과 문장 적합도와 검토 상태를 제공한다.

### 2.3 동의·보안·운영자 접근

- 이용 데이터 분석은 필수 약관과 분리된 선택 동의이며 기본값은 꺼짐이다. 설정에서 철회할 수 있고 동의 버전을 함께 저장한다.
- 분석 테이블과 RPC는 브라우저 역할에 공개되지 않고 service role만 접근한다. 계정 삭제 시 분석 이벤트는 cascade 삭제된다.
- 관리자 페이지는 서버 인증, 관리자 허용 목록, 활성 계정, 운영자 계정 동기화를 통과해야 하며 `/admin` 전체가 동적·비색인 페이지다.
- 기존 90일 삭제 작업과 계정 삭제 cascade는 유지한다. 더 긴 기간의 비식별 집계 보존은 별도 검토 전까지 도입하지 않는다.

## 3. 지표 체계

모든 비율은 분자·분모·관찰 기간·대상 집단을 함께 표시한다. 데이터가 없거나 저장소를 읽지 못한 경우 `0`으로 위장하지 않고 각각 “아직 표본 없음”, “집계 연결 필요”로 표시한다.

### 3.1 핵심 퍼널

| 단계 | 지표 | 권장 이벤트/사실 원천 | 분모 | 베타 판정 |
| --- | --- | --- | --- | --- |
| 발견 | 검사·함께하기 진입 사용자 | `screen_view(area=assessment/together)` | 동의 활성 사용자 | 진입 규모와 유입 영역 확인 |
| 시작 | 검사 시작 사용자 | 향후 `assessment_started`; 현재는 assessment 화면 사용자 대용 | 진입 사용자 | 시작률 |
| 진행 | 첫 응답·25%·75% 도달 | 향후 `assessment_progressed`; 답변 값은 금지 | 시작 사용자 | 초반·중반 이탈 위치 |
| 완료 | 완료 사용자 | `assessment.assessment_attempt`의 완료/소유권 확정 사실 | 시작 사용자 | 핵심 완료율 |
| 결과 확인 | 결과 화면 사용자 | `screen_view(area=result)`, 향후 `result_viewed` | 완료 사용자 | 완료 후 결과 도달률 |
| 결과 도움 | 도움 응답 사용자 및 긍정률 | 향후 `result_helpfulness_submitted`; 현재 `core_result_feedback`은 문장 적합도 대용 지표 | 도움 질문 노출 사용자 | 결과가 행동·관계 이해에 도움됐는지 |
| 확장 가치 | 공유·비교 사용자 | `sharing.share_link`, `comparison.public_comparison_report`, 향후 명시 이벤트 | 완료 사용자 | 소셜 확장률 |
| 재방문 | 2개 이상 서로 다른 날짜에 활동한 사용자 | 동의 기반 화면 이벤트 | 기간 활성 사용자 | 반복 가치 |

`fit`은 “도움이 됐다”와 같은 뜻이 아니다. 운영 화면과 보고서에서 현재 결과 문장 적합도는 도움 지표의 대용 신호라고 명시하고, 두 값을 합산하지 않는다.

### 3.2 활성화

- 베타 1차 활성화: 계정 생성 후 24시간 안에 첫 검사를 완료한 사용자.
- 소셜 활성화: 첫 검사 완료 후 7일 안에 공유 또는 비교를 1회 이상 수행한 사용자.
- 함께하기 활성화: 방 생성 또는 참여 후 결과 화면까지 도달한 사용자.
- 현재 집계는 분석에 동의한 로그인 계정만 사용한다. 비로그인 밸런스게임 참여자는 별도 선택 동의 UX와 익명 식별 계약이 완성되기 전까지 사용자 퍼널에 결합하지 않는다.

### 3.3 완료·결과 품질

- 검사 완료 사용자/건수, 완료 사용자당 결과 화면 조회 수.
- 결과 문장 적합도: `fit / 전체 응답`, 상황 의존: `depends / 전체`, 불일치: `not_fit / 전체`.
- 결과 도움 질문은 “이 결과가 나를 이해하거나 대화를 시작하는 데 도움이 됐나요?”처럼 하나의 의미만 묻고 `helpful`, `neutral`, `not_helpful`로 저장한다.
- 표본 10명 미만은 비율 대신 “표본 수집 중”으로 표시한다. 세부 버전 비교는 표본 20명 이상에서만 운영 판단에 사용한다.

### 3.4 재방문·공유·비교

- D1/D7 재방문은 첫 활성화일을 0일로 둔 고정 코호트로 계산한다.
- 단기 운영 화면의 “반복 사용자”는 선택 기간에 서로 다른 2일 이상 화면 이벤트가 있는 사용자로 정의한다.
- 공유율과 비교율은 각각 해당 기간 완료 사용자 중 1회 이상 공유·비교한 고유 사용자 비율이다. 생성 건수와 사용자 수를 분리한다.
- 공유 버튼 클릭은 의도, 실제 share link/피드 공유 저장은 성공이다. 성공률은 성공/의도로 계산하며 향후 두 이벤트를 모두 수집한다.

### 3.5 오류·불편

- 현재 오류 신호: `product_feedback.kind=bug`; 사용성 신호: `kind=usability`.
- 향후 자동 오류 지표: API 5xx/timeout, 화면 복구 불가 오류, 검사 저장 실패, 밸런스게임 생성·참여·응답·완료 실패.
- 자동 오류 이벤트에는 메시지·stack·URL을 원문 저장하지 않는다. `error_code`, `area`, `operation`, `release`, `recoverable`만 허용하며 예상 가능한 4xx 검증 오류와 네트워크 취소는 별도 분류한다.
- 오류율 분모는 동일 작업 시도 수다. 오류 건수만으로 기능 품질을 비교하지 않는다.

## 4. 이벤트 계약

### 4.1 공통 봉투

향후 이벤트 테이블은 다음 허용 목록 필드만 받는다.

| 필드 | 설명 | 제한 |
| --- | --- | --- |
| `schema_version` | 이벤트 계약 버전 | 서버 허용 버전만 |
| `event_name` | 아래 카탈로그 값 | 자유 입력 금지 |
| `event_id` | 재시도 중복 제거 UUID | 이벤트당 1개 |
| `occurred_at` | 클라이언트 발생 시각 | 서버 시각 ±24시간 밖이면 서버 시각 사용 |
| `area` | 정규화 제품 영역 | 기존 9개 영역 |
| `flow` | `core_assessment`, `topic_assessment`, `balance_game`, `community`, `profile` 등 | enum |
| `step` | `landing`, `setup`, `question`, `result` 등 | enum |
| `outcome` | `started`, `completed`, `cancelled`, `failed` 등 | enum |
| `content_version` | 검사·문구 릴리스 버전 | 120자 이하, 사용자 입력 금지 |
| `session_key` | 회차 연결용 서버 해시 | 원본 세션 ID 저장 금지 |
| `account_id` | 로그인 계정 | 서버에서만 주입 |
| `anonymous_id_hash` | 향후 익명 선택 동의 사용자 | 서버 pepper HMAC, 원본 저장 금지 |
| `properties` | 이벤트별 허용된 작은 속성 | 1KB 이하, 중첩 1단계 |

금지 필드: 검사 답변·점수 원문, 결과 코드가 포함된 전체 payload, 자유 텍스트, 검색어, 피드 내용, 댓글, 닉네임, 방 이름·참여 코드, 이메일·전화번호, IP·user-agent 원문, pathname/query/hash, 공개·비공개 프로필 ID.

### 4.2 카탈로그

- 화면: `screen_view`
- 검사: `assessment_started`, `assessment_progressed`, `assessment_completed`, `assessment_abandoned`
- 결과: `result_viewed`, `result_helpfulness_prompted`, `result_helpfulness_submitted`
- 공유·비교: `share_started`, `share_completed`, `comparison_started`, `comparison_created`, `comparison_viewed`
- 밸런스게임: `balance_room_created`, `balance_room_joined`, `balance_round_completed`, `balance_result_viewed`
- 피드백: `feedback_submitted`
- 안정성: `operation_failed`, `web_vital_sampled`

전환 성공 이벤트는 분석 이벤트보다 canonical DB 성공 사실을 우선한다. 예를 들어 검사 완료는 클라이언트 `assessment_completed`와 저장된 attempt가 다르면 저장된 attempt를 기준으로 한다.

## 5. 식별과 동의

### 5.1 로그인 사용자

- 브라우저는 account ID를 보내지 않는다. 서버가 검증된 사용자에서 account ID를 해석한다.
- 현재 분석은 활성 계정이고 현재 분석 동의 버전에 명시적으로 동의한 사용자만 기록한다.
- 계정 병합 중이거나 계정·동의 확인이 실패하면 수집하지 않는다.

### 5.2 비로그인 사용자

- 현재 단계에서는 자동 제품 분석을 수집하지 않는다. 사용자가 직접 제출한 제품 의견만 기존 계약대로 처리한다.
- 향후 별도 선택 UI가 승인되면 브라우저에서 임의 ID를 만들고 30일마다 회전한다. 서버에는 pepper HMAC 값만 보낸다.
- 로그인 전 이력을 로그인 계정에 소급 결합하지 않는다. 사용자가 명확히 동의한 회차의 전환 연결이 필요하면 단기 `session_key`만 사용하고 24시간 내 폐기한다.

### 5.3 Do Not Track와 선택 동의

- `navigator.doNotTrack === "1"`, `window.doNotTrack === "1"` 또는 향후 Global Privacy Control이 활성화되면 분석 선택 동의가 있어도 브라우저 이벤트 전송을 중단한다.
- DNT를 해제하더라도 사용자가 선택 동의를 하지 않았다면 수집하지 않는다.
- 선택 동의 확인이 실패하면 fail-closed로 수집하지 않는다.
- 철회는 다음 이벤트부터 즉시 중단한다. 기존 raw 이벤트는 현재 90일 보존 및 계정 삭제 cascade를 따른다. 철회 시 과거 이벤트 즉시 삭제 정책은 별도의 정책 승인 전까지 도입하지 않는다.

## 6. 보존·최소화·샘플링

- raw 제품 분석 이벤트: 현재와 동일하게 최대 90일.
- 개인 연결이 없는 일별 집계: 아직 만들지 않으며, 향후 최소 코호트 20명과 별도 승인 후 최대 13개월을 제안한다.
- 제품 의견 본문과 결과 품질 의견은 제품 분석 이벤트와 합치지 않고 기존 운영 저장소·권한을 유지한다.
- 전환·완료·오류 성공/실패: 동의 사용자 100%, 서버 rate limit 적용.
- `screen_view`: 100%이되 동일 계정·영역 5분 중복 제거.
- 진행률 이벤트: 시작 후 최초 25%·75% 각 1회만.
- Web Vitals: 동의 사용자 세션의 결정적 10% 표본. 표본 여부는 안정적인 세션 해시로 결정한다.
- 반복 오류: 같은 `error_code + operation`은 세션당 최대 3회, 서버에서 분당 상한을 둔다.

## 7. 운영센터 정보 구조

### 7.1 필터

- 기간: 7일, 30일, 90일. 기본 30일.
- 향후: 제품 영역, flow, 검사 릴리스, 로그인/익명 집단, 신규/기존 사용자.
- 소표본 필터 결과는 개인 추론을 막기 위해 숨기며 최소 코호트 20명을 적용한다.

### 7.2 화면

1. 수집 상태: 현재 동의 버전, 동의 활성 계정, 관찰 사용자, 마지막 이벤트, 보존기간.
2. 핵심 카드: 기간 활성 사용자, 화면 조회, 반복 사용자, 사용자당 조회.
3. 핵심 퍼널: 진입, 시작, 완료, 결과 확인, 공유, 비교. 현재 수집할 수 없는 단계는 “계측 예정”으로 표시한다.
4. 일별 추이: 화면 조회와 고유 사용자. 0인 날짜도 표시한다.
5. 영역 분포: 조회 수와 고유 사용자. 정규화 영역만 표시한다.
6. 가치·품질: 활성화, 완료율, 결과 도움, 결과 문장 적합도, 공유·비교율.
7. 오류·불편: 자동 오류율, 버그·사용성 의견. 자동 오류 미계측 시 의견 건수임을 분명히 표시한다.

빈 상태는 다음 세 가지를 구분한다.

- 정상·표본 없음: “선택한 기간에 수집된 이용 데이터가 없습니다.”
- 마이그레이션 미적용: “제품 분석 집계 저장소 연결이 필요합니다.”
- 일부 모듈 실패: 성공한 집계는 보여주고 실패 모듈과 재시도 안내를 표시한다.

### 7.3 권한

- 활성 관리자이면서 `identity.operator_account`에 등록된 계정만 집계 RPC를 호출할 수 있다.
- 운영 UI에는 account ID, 익명 해시, 이벤트 행, 원본 의견 본문을 결합한 사용자 타임라인을 제공하지 않는다.
- CSV 내보내기와 개인 드릴다운은 MVP 범위에서 제공하지 않는다.
- 기간·필터 조회는 읽기 전용이며 별도 관리자 변경 기록을 만들지 않는다. 지표 정의·보존·샘플링 변경은 코드 리뷰와 릴리스 기록이 필요하다.

## 8. 성능 예산

### 8.1 사용자 화면

- 초기 번들 증가: gzip 2KB 이하.
- 렌더·입력 경로 동기 실행: 이벤트당 2ms 이하.
- 화면 이벤트는 idle 시점에 전송하고 페이지 전환을 기다리게 하지 않는다.
- 요청 body: 4KB 이하. 향후 배치는 최대 20개/16KB, 15초 또는 페이지 종료 시 전송한다.
- 화면 조회는 동일 영역 5분 중복 제거하며 분석 네트워크 실패를 재시도 루프로 만들지 않는다.
- API p95: warm 150ms 이하, cold 500ms 이하. 사용자 기능 응답과 같은 트랜잭션에 분석 쓰기를 넣지 않는다.

### 8.2 운영 화면

- 개인 이벤트 목록을 내려받지 않고 DB에서 집계한 JSON 한 건만 받는다.
- 기본 30일 집계 p95 500ms, 90일 p95 1초 이하.
- 응답 JSON 100KB 이하, 일별 최대 90개·영역 최대 9개.
- `occurred_at`, `account_id`, `area` 기존 인덱스를 활용하고 `EXPLAIN (ANALYZE, BUFFERS)`로 10만·100만 이벤트에서 검증한다.

## 9. 단계별 구현 결정

### Phase 0 — 이번 구현

- DNT를 즉시 존중하고 화면 분석 전송을 idle 시점으로 이동한다.
- 현재 로그인·선택 동의 `screen_view`와 기존 canonical 완료·공유·비교·품질 사실을 개인 식별자 없이 집계하는 관리자 RPC를 추가한다.
- `/admin/analytics`에 7/30/90일 필터, 수집 범위, 핵심 카드, 일별 추이, 영역 분포, 현재 계측 한계, 빈 상태를 추가한다.
- 현재 동의 버전이 아닌 계정은 신규 화면 이벤트 기록과 관리자 대상 집계에서 제외한다.

### Phase 1 — 베타 핵심 퍼널

- 이벤트 공통 봉투와 허용 카탈로그를 DB·Zod에 동일하게 정의한다.
- 검사 시작·진행·결과 도움, 공유 의도·성공, 비교 성공, 밸런스게임 결과 도달을 계측한다.
- 이벤트 배치, 서버 중복 제거, rate limit, 오류 코드 상한을 적용한다.
- 퍼널·릴리스 필터와 자동 오류율 차트를 활성화한다.

### Phase 2 — 익명 선택 동의와 코호트

- 비로그인용 별도 선택 동의 UX, 30일 회전 익명 ID, 24시간 session key를 검토한다.
- D1/D7 고정 코호트, 익명→로그인 전환은 소급 병합 없이 집계한다.
- 최소 코호트 20명 미만 숨김과 비식별 일별 집계 보존을 검증한다.

## 10. 검증 체크리스트

- DNT=1이면 네트워크 요청이 0건이다.
- 로그인하지 않았거나 분석 동의가 없으면 DB 이벤트가 0건이다.
- 원본 path/query/result ID가 요청·DB·운영 화면에 없다.
- 현재 동의 버전이 아니면 RPC가 `not_allowed`를 반환한다.
- 운영자가 아니면 분석 집계 RPC가 거부된다.
- 7/30/90일 이외 입력은 거부된다.
- 일별 데이터가 없는 날짜도 0으로 채워지고 시간대는 UTC 일자를 기준으로 일관된다.
- 집계 저장소 오류와 정상 0건이 다른 UI로 보인다.
- 분석 API/DB 장애 상태에서 핵심 사용자 흐름 E2E가 그대로 통과한다.
- 사용자 화면 Lighthouse/INP와 분석 비활성 기준의 차이가 성능 예산 안이다.

## 11. 운영 리듬

- 매일: 오류·불편 증가, 마지막 이벤트 지연, 집계 unavailable 확인.
- 매주: 활성화·완료·결과 적합도·반복·공유·비교를 같은 7일 창으로 검토하고 제품 변경 로그와 함께 해석한다.
- 릴리스 후 48시간: 이전 7일 동일 요일 대비 완료율·오류율·응답속도 회귀를 확인한다.
- 의사결정에는 표본 수, 수집 동의 범위, 릴리스 버전, 알려진 계측 누락을 반드시 함께 기록한다.
