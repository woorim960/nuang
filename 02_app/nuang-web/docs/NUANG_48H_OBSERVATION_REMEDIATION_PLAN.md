# 뉴앙 48시간 운영 관찰 개선 실행 계획

기준일: 2026-08-21
대상: `nuang.app` 운영 모니터, 피드 읽기 경로, 운영 이메일, Supabase/R2 용량 게이트

## 1. 목표와 원칙

이번 개선의 목표는 단순히 경고 수를 줄이는 것이 아니다. 고객이 실제로 느끼는 장애와 점검 도구 자체의 실패를 정확히 구분하고, 간헐적인 피드 지연을 재현 가능한 지표로 바꾸며, 무료 운영 한도를 넘기기 전에 안전하게 대응할 수 있는 운영 계약을 만드는 것이다.

모든 작업은 다음 원칙을 지킨다.

- 운영 확인은 저부하·읽기 전용으로 유지한다.
- 실제 서비스 장애는 실패-폐쇄하되, 모니터 실행 실패를 고객 장애로 오인하지 않는다.
- 비밀값, 사용자 정보, 응답 본문, 저장 경로는 로그와 이메일에 남기지 않는다.
- 변경은 로컬 테스트와 정적 계약을 먼저 통과한 뒤 배포한다.
- 배포 후 검증은 공개·비인증 경계만 사용하고, 쓰기 smoke나 내부 drain은 별도 승인 없이는 실행하지 않는다.

## 3. 문제 정의

### 3.1 모니터 종료 경계

이메일 래퍼는 자식 모니터를 90초 뒤 `SIGTERM`으로 종료한다. 그러나 HTTP 초기 점검, 지연 경로 재확인, DB 점검, 선택적인 R2 점검을 모두 합친 합법적인 최악 시간은 90초를 넘을 수 있다. timeout과 출력 초과, 외부 종료도 모두 최종적으로 `monitor_signal_SIGTERM`처럼 보이므로 원인 판별이 어렵다.

개선 계약:

- HTTP 단계는 정해진 동시성 안에서 초기 점검과 재확인을 모두 제한한다.
- 전체 자식 실행 예산은 하위 단계의 최악 예산보다 충분히 크게 잡는다.
- timeout, 출력 초과, spawn 오류, 외부 signal을 서로 다른 안전한 error code로 반환한다.
- 정상 JSON을 얻은 뒤 남은 kill timer가 프로세스를 건드리지 않게 정리한다.
- 종료 요청 후 grace 기간이 지나도 자식이 남으면 강제 종료해 래퍼가 영구 정체되지 않게 한다.

합격 기준:

- 느린 모의 점검이 기존 90초 경계를 넘어도 새 예산 안에서는 성공한다.
- 새 예산을 넘기면 `monitor_timeout`으로만 보고된다.
- 출력 초과는 `monitor_output_too_large`, 외부 signal은 `monitor_signal_*`로 구분된다.
- 자식 프로세스·timer·listener가 테스트 종료 후 남지 않는다.

### 3.2 HTTP tail latency와 진단 가능성

현재 HTTP detail은 TTFB와 전체 시간만 보여 준다. 헤더 수신 뒤 본문 전송이 느린지, 응답 검증이 실패했는지, 전체 요청이 timeout인지 분리하기 어렵다. 본문 읽기 오류를 빈 본문으로 바꾸기 때문에 `bytes=0`이 네트워크 실패인지 실제 빈 응답인지도 불명확하다.

개선 계약:

- `ttfb`, `transfer`, `total`, `bytes`를 분리한다.
- 헤더 이전 실패와 본문 읽기 실패를 구분한다.
- 본문 읽기에도 명시적인 deadline과 취소를 적용한다.
- 지연 재확인은 최대 동시성 2를 유지해 저부하이면서도 전체 시간을 제한한다.
- 지연만 회복되면 정상 회복으로 처리하고, 상태·본문·보안 헤더 실패는 완화하지 않는다.

합격 기준:

- header timeout은 `phase=headers`, body timeout은 `phase=body`로 구분된다.
- 정상 응답은 `ttfb`, `transfer`, `total`, 검증 결과를 모두 포함한다.
- 여러 경로가 동시에 느려도 재확인 동시성은 2 이하이고 순차 재확인보다 짧은 상한을 갖는다.

### 3.3 경보 등급과 이메일 전달

고객 경로 실패와 모니터 실행 실패가 모두 같은 긴급 표현을 사용한다. 운영자는 고객 장애인지 점검 도구 장애인지 이메일 제목만으로 판단하기 어렵다.

개선 계약:

- 실제 서비스 check 실패는 기존 `긴급`을 유지한다.
- 유일한 실패가 `monitor:execution`이면 `점검 실패` 표현을 사용한다.
- 회복, 주의, 정상, 실제 실패의 기존 idempotency 계약을 유지한다.
- 예상하지 못한 일반 `Error`는 그대로 노출하지 않고 `monitor_email_unavailable`로 정규화한다.

합격 기준:

- 고객 장애와 점검 실패가 서로 다른 제목·배지를 가진다.
- 공급자 본문이나 내부 오류 메시지는 이메일·JSON에 포함되지 않는다.
- Resend 429/5xx·네트워크·409 계약의 기존 회귀 테스트가 모두 통과한다.

### 3.4 Supabase/R2 비용과 용량

DB SQL은 현재 프로젝트 Storage와 DB 크기를 확인하지만 조직 전체 Egress·MAU·Storage는 확인하지 못한다. R2는 개인정보 회신 전까지 고객 쓰기를 켜면 안 된다.

개선 계약:

- 시간별 자동 점검: DB 크기·연결·현재 프로젝트 Storage·R2 ledger/실사용량.
- 매일 수동 점검: Supabase Egress·MAU·조직 Storage, Resend Usage, Cloudflare Billing.
- R2 고객 쓰기: 개인정보 회신·고지 승인·합성 smoke·운영자 1명 카나리 순서를 통과한 뒤에만 허용.

합격 기준:

- 운영 가이드에 대시보드 위치, 기록 항목, 경고선, 중단 조건이 명시된다.
- 회신 전 `FEED_MEDIA_WRITE_PROVIDER=supabase`와 개인정보 승인 false를 유지한다.

## 4. 단계별 실행 순서

### 단계 A — 점검 기반 안정화

1. 자식 모니터 실행기를 테스트 가능한 모듈로 분리한다.
2. 전체 예산, 종료 grace, 출력 상한을 상수와 계약으로 정의한다.
3. HTTP 재확인을 동시성 2로 제한해 전체 예산을 줄인다.
4. 종료 원인을 timeout/output/spawn/signal로 구분한다.
5. 단위·통합 테스트를 통과시킨다.

배포 게이트: 모니터와 이메일 테스트, lint, format, diff-check 통과.

### 단계 B — 지연 진단과 경보 품질

1. HTTP probe에 `transferMs`와 단계별 오류를 추가한다.
2. body read 실패를 빈 응답으로 숨기지 않는다.
3. `monitor:execution` 전용 이메일 표시를 추가한다.
4. 예상하지 못한 메일 오류 코드를 안전하게 정규화한다.

배포 게이트: 공개 HTML·feed JSON·401 no-store 경계 테스트 통과.

### 단계 C — 운영 비용 게이트

1. Supabase Usage의 Egress·MAU·Storage를 매일 같은 시각에 기록한다.
2. Resend 일일/월간 사용량을 함께 기록한다.
3. R2는 Standard/IA/Class A/B와 객체 정합성을 자동 점검하고 Billing을 수동 대조한다.
4. 개인정보 회신 전 Supabase 쓰기를 유지한다.

배포 게이트: 운영자가 값·날짜·판정을 한 줄로 기록할 수 있는 체크리스트 완성.

### 단계 D — 배포 후 재관찰

1. 배포 직후 공개·비인증 저부하 점검 1회.
2. 24시간 동안 시간별 결과에서 `monitor_timeout`·외부 signal·HTTP timeout 빈도를 집계한다.
3. customer check fail이 2회 연속이면 Vercel 상태·최근 1시간 로그를 확인한다.
4. 모니터 실행 실패만 발생하면 고객 장애로 단정하지 않고 실행기 진단을 우선한다.

최종 합격 기준:

- `monitor_signal_SIGTERM` 재발 0회.
- 모니터 자체 timeout 발생 시 원인이 `monitor_timeout`으로 명확함.
- 정상 시 최대 HTTP와 DB 지표가 계속 보고됨.
- 서비스 경로 실패와 점검 도구 실패가 이메일 제목에서 구분됨.
- DB·Supabase 사용량이 경고선 아래이며 R2 고객 쓰기는 승인 게이트를 지킴.

### 5.2 최초 배포 사후검증과 롤백

2026-08-21 최초 배포 `a744d56`은 Vercel에서 Ready가 됐지만, 공개 사후검증에서
`/api/feed`가 500을 반환해 완료 판정을 보류했다. 런타임 로그에서 GET과 같은
라우트에 묶인 POST용 `sharp`가 Linux `libvips` 없이 초기화되는 패키징 오류를
확인했다. 운영 별칭은 즉시 직전 정상 배포 `02ff460`으로 롤백했고, 공개 피드 API
200 복구를 확인했다.

재발 방지 변경:

- GET은 POST 전용 미디어 서버를 초기화하지 않도록 동적 import 경계를 둔다.
- 이미지 최적화가 실제 호출될 때만 `sharp`를 불러온다.
- `/api/feed` 함수 추적에 Linux x64용 `sharp`와 `libvips`를 명시한다.
- 이미지 런타임 import가 실패해도 공개 GET이 200인 격리 회귀 테스트를 유지한다.
- Linux 파일 추적 계약을 Next 설정 테스트로 고정한다.

수정 배포는 타깃 테스트, 전체 회귀, 프로덕션 빌드를 다시 통과한 뒤에만 진행한다.

## 6. 롤백 기준

- 모니터 변경으로 메일 누락·중복이 발생하면 이메일 래퍼 변경만 이전 버전으로 되돌린다.
- HTTP probe가 운영 부하를 늘리면 동시성을 1로 낮추되 전체 child timeout을 줄이지 않는다.
- 실제 고객 경로 실패가 새 분류에서 완화되면 즉시 이전 fail 판정을 복구한다.
- R2 관련 불확실성이 하나라도 있으면 신규 쓰기를 Supabase로 유지하고 기존 R2 읽기·삭제 안전장치는 보존한다.
