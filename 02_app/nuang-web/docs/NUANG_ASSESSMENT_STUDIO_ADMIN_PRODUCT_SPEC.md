# 뉴앙 검사 스튜디오 통합 운영 플랫폼 최종 기획서

문서 버전: 1.0
작성일: 2026-08-03
대상: 빠른 코어, 정밀 코어, 주제 검사, 별난 연구소, 함께하기

## 1. 제품 결론

운영센터에 `검사 스튜디오`를 신설한다. 이 화면은 단순한 문구 CRUD가 아니라 검사 하나의 기획, 문항, 채점, 결과, 공유, 검수, 발행, 중지, 롤백을 한 버전으로 묶어 운영하는 통합 제작·관리 도구다.

가장 중요한 수용 기준은 다음 한 문장이다.

> 운영자가 새 버전을 발행하면 모든 신규 진입점은 같은 버전을 사용하고, 이미 시작한 검사·완료 결과·함께하기 방은 당시 버전으로 온전히 재현되어야 한다.

게시된 콘텐츠는 직접 덮어쓰지 않는다. 변경은 항상 새 작업본으로 만들고, 자동 검증과 검토를 거쳐 불변 릴리스로 발행한다. `삭제`는 기본적으로 안전한 보관이며, 영구 삭제는 공개된 적도 없고 사용자 데이터와 연결되지 않은 초안에만 허용한다.

## 2. 현행 전수 감사

| 유형 | 현재 원본 | 확인된 규모 | 핵심 위험 |
|---|---|---:|---|
| 빠른 코어 | TypeScript 후보 릴리스 | 기본 22문항, 추가 확인 최대 15문항 | 채점·이어하기·결과가 릴리스 ID를 하드코딩 |
| 정밀 코어 | TypeScript 후보 릴리스 | 기본 60문항, 추가 확인 최대 15문항 | 문항만 바꾸면 빠른 검사 재사용·채점과 불일치 가능 |
| 주제 검사 | TypeScript 검사/문항/리포트 원장 | 전체 19개, 공개 후보와 운영 공개가 혼재 | 문항, 채점, 장문 리포트, 근거 버전이 분산 |
| 별난 연구소 | TypeScript 검사/프로필 원장 | 3개, 각 6문항·3프로필 | 정책 문서와 실제 저장·공유 동작이 일부 불일치 |
| 밸런스 게임 | 코드 팩 + DB 방 스냅샷 | 8팩, 총 312문항 | 방 생성 시 코드가 DB를 동기화해 운영 수정이 되돌아갈 수 있음 |
| 친구 성향 맞히기 | 컴포넌트와 초대 URL | 1개 장면, 2개 선택지 | 선택지 ID를 바꾸면 기존 초대 링크 의미가 깨짐 |

기존 `검사 연구`는 사용자 피드백·연구 판단을, `성향 콘텐츠`는 성향지도와 결과 리포트 데이터센터를 관리한다. 새 `검사 스튜디오`는 실제 고객이 실행하는 검사·놀이 정의를 담당하며 두 메뉴를 대체하지 않는다.

## 3. 범위와 비목표

### 포함

- 모든 기존 검사와 문항을 한 카탈로그에서 검색·열람
- 운영자 신규 검사·팩·문항 등록
- 제목, 설명, 안내, 문항, 보기, 결과 유형·리포트, 노출 설정 수정
- 복제, 순서 변경, 검토 요청, 발행, 일시 중지, 보관, 복원, 롤백
- 유형별 자동 검증과 모바일 미리보기
- 변경 사유, 작성자, 게시자, 시각, 이전·이후 값 감사 기록
- 발행 릴리스를 앱 시작, 채점, 결과, 공유와 연결

### 비목표

- 운영자가 임의 JavaScript 채점 코드를 작성하는 기능
- 게시된 버전의 직접 수정
- 과거 결과를 새 채점 기준으로 조용히 재계산
- 공개 검사·사용자 결과의 물리적 삭제
- 자동화가 측정 의미나 게시 승인을 대신하는 기능

## 4. 운영자 정보 구조

`검사 스튜디오`는 다음 화면으로 구성한다.

1. **개요**: 운영 중, 검토 중, 중지, 보관, 게시 차단, 버전 불일치 수
2. **카탈로그**: 유형·상태·담당자·품질 경보·최근 변경을 검색/필터
3. **편집기**: 기본 정보, 문항, 채점·결과, 품질, 미리보기, 버전·공개
4. **검토함**: 검토 요청, 수정 요청, 승인 대기, 장기 미처리
5. **릴리스**: 현재 버전, 작업본, 변경 비교, 중지, 롤백
6. **품질 신호**: 퍼널, 이탈, 판단 어려움, 결과 적합도, 분포, 공유, 재검사

첫 구현에서는 개요·카탈로그·편집기·검증·릴리스 동작을 한 반응형 화면에 통합하고, 품질 신호는 기존 검사 연구 화면과 연결한다.

## 5. 공통 편집기

### 5.1 기본 정보

- 고객용 제목, 한 줄 설명, 상세 설명
- 안정적인 slug와 내부 유형
- 예상 시간, 전 연령/성인 인증, 민감도
- 결과 저장, 이어하기, 재검사, 공유 정책
- 홈 분류, 노출 순서, 추천 여부
- 담당자와 변경 사유

slug·유형은 최초 공개 후 잠근다. 고객 제목과 설명은 수정할 수 있지만 새 릴리스로 발행한다.

### 5.2 문항

- 문항 ID, 순서, 섹션/상황, 문항 문구
- 보기 ID, 문구, 내부 값
- 측정 차원·세부 축·정/역채점 또는 결과 유형 연결
- 민감도, 판단 어려움, 출처, 검토 상태
- 복제, 위/아래 이동, 추가, 안전 보관

문항 ID는 결과 재현성의 핵심이므로 공개 후 재사용하거나 다른 의미로 바꾸지 않는다.

### 5.3 채점·결과

운영자는 개발자가 허용 목록에 등록한 엔진과 설정만 선택한다.

- 코어: 엔진·채점·코드 체계·문항은행 릴리스 묶음
- 주제: 척도, 역채점, 결측 규칙, 결과 구간, 장문 리포트
- 별난 연구소: 보기→프로필 매핑, 동률, 프로필별 강점·주의·관계 팁·작은 실험
- 밸런스: 취향 일치·상호보완·발견형 의미와 문항 풀 구성
- 친구 맞히기: 발신자 실제 선택, 상대 예상, 수신자 실제 선택의 결과 조합

### 5.4 품질 검증

검증 결과는 `발행 차단`, `개선 권고`, `참고`로 나눈다. 발행 차단이 하나라도 있으면 게시할 수 없다.

### 5.5 실제 화면 미리보기

- 320/360/390/430px 프리셋
- 시작 카드, 문항, 결과 핵심, 공유 카드
- 긴 문구 overflow, 터치 영역, 키보드, 스크린리더 이름 확인
- 운영 내부 필드는 미리보기에서 제외

## 6. 유형별 편집·검증 계약

### 6.1 빠른 코어

- 5개 코드 위치와 세부 축 커버리지
- 정/역문항 균형, 응답 형식, 추가 확인 트리거
- 판단 어려움·일자 응답·불충분 근거 처리
- 로컬 저장, 로그인 귀속, 기기 간 복원, 재검사 계약
- 정밀 검사 연결과 응답 재사용 영향 표시

채점에 영향을 주는 문항 추가·삭제·축·역채점 변경은 등록된 채점 릴리스가 없으면 발행을 차단한다. 일반 운영자는 문구 편집은 할 수 있지만 내부 축·역채점은 잠금 상태로 본다.

### 6.2 정밀 코어

- 60개 기본 문항의 5축·세부 축 커버리지
- 빠른 검사 선행·응답 재사용 계약
- 추가 확인과 동률 해결
- 대표 코드, 세부 성향, 성향지도, 비교 결과 영향

문항은행·채점·코드 체계·결과 리포트 중 하나만 따로 활성화하지 못하고 하나의 호환 릴리스로 발행한다.

### 6.3 주제 검사

- 한 문장 구성개념과 포함/제외 경계
- 차원×공통 상황 청사진, 회상 기간, 응답 척도
- 문항별 대상·행동 하나, 차원당 최소 커버리지
- 높은/중간/낮은 결과 문구
- 핵심 성향, 답변 근거, 강점, 불편해질 수 있는 지점, 개선 행동, 가까운 사람의 도움, 뉴앙 코드 교차 해석
- 결과 주장 `claimId`와 연구 근거 연결

모호한 대상 혼합, 이중 질문, 번역체, 모든 결과의 과도한 긍정 포장을 경고한다.

### 6.4 별난 연구소

- 놀이 목적과 안전 경계
- 질문·보기·프로필 매핑
- 도달 불가능한 프로필과 동률 처리
- 프로필별 핵심 모습, 강점, 주의점, 관계 팁, 작은 실험
- 서버 저장·공유·삭제 정책

### 6.5 밸런스 게임

팩 설정:

- 팩 제목·설명·채점 템플릿·결과 의미
- 기본/지원 문항 수, 라운드 크기, 콘텐츠 풀 버전
- 대상 관계, 민감도, 소규모/공개 모집 정책

문항 설정:

- 질문, A/B 보기, 하위 주제, 단계, 강도, 대상 관계
- 채점 포함, 하이라이트 우선순위, 대화 가치
- 상호보완형 `meaningCode`와 선호/자기 행동 짝

자동 검증:

- ID·질문·보기 조합 중복, 동일한 A/B
- 질문 44자·보기 28자 모바일 권고
- 최대 게임 길이보다 작은 문항 풀
- 팩/문항 버전 불일치와 상호보완 짝 누락
- 하위 주제·긍정 답안 편중

진행 중인 방은 생성 당시 팩 릴리스에 고정한다. 새 발행은 새 방에만 적용한다.

### 6.6 친구 성향 맞히기

밸런스 팩이 아니라 `invite_prediction` 실행 템플릿으로 관리한다.

- 장면, 두 보기, 발신자/수신자 안내, 초대 결과 문구
- 초대 만료, 링크 서명, 저장·공유 범위
- 선택지 안정 ID

기존 `plan`·`listen` ID는 현재 초대 링크와 연결되어 있으므로 변경을 차단한다.

## 7. 상태와 버전

편집 상태와 고객 공개 상태는 내부적으로 분리한다. 첫 구현 UI에서는 이해하기 쉽게 아래 생명주기로 표현한다.

`작성 중 → 검토 중 → 게시됨 → 일시 중지 → 보관됨`

- **작성 중**: 운영자만 열람, 자유롭게 저장
- **검토 중**: 변경 목적과 자동 검증 결과를 묶어 검토
- **게시됨**: 불변 스냅샷 생성, 모든 신규 실행에 사용
- **일시 중지**: 신규 시작·노출만 차단, 기존 결과 재열람 유지
- **보관됨**: 카탈로그 기본 목록에서 제외, 감사·복원 가능

발행 때 `release key`, 연속 버전 번호, 콘텐츠 해시, 변경 사유, 게시자를 저장한다. 작업본과 현재 공개본이 다르면 `미발행 변경`으로 표시한다.

## 8. 데이터와 런타임 원칙

첫 구현의 공통 원장은 다음 두 계층이다.

- `assessment_content_entry`: 검사 정체성과 현재 작업본
- `assessment_content_release`: 발행 당시 전체 실행 문서의 불변 스냅샷

실행 문서는 공통 표지와 유형별 payload로 구성한다. JSON은 임의 데이터 저장소가 아니라 유형별 스키마 검증을 통과한 **컴파일된 릴리스 스냅샷**이다. 화면은 공통 JSON 편집기가 아니라 각 유형의 전용 폼을 사용한다.

향후 문항은행 공동 사용과 역할별 승인 규모가 커지면 `item_revision`, `scoring_release`, `report_release`, `evidence_release`, `publication_release`로 물리 분리하되, 현재 릴리스 스냅샷 계약은 유지한다.

앱은 다음 순서로 콘텐츠를 해석한다.

1. 게시된 DB 릴리스 조회
2. 유형별 스키마·엔진 호환성 검증
3. 통과하면 해당 릴리스 사용
4. DB 미적용/장애/비호환이면 번들 기본본 사용
5. 시작한 회차에는 사용 릴리스 ID와 스냅샷 고정

번들 파일은 초기 이관과 비상 복구용이며, DB 게시본을 역으로 덮어쓰지 않는다.

## 9. 권한·승인·감사

- 모든 조회·수정 API는 서버에서 관리자 권한 확인
- 브라우저 쓰기 요청은 same-origin 검사
- 테이블은 일반 익명·로그인 사용자 접근 차단
- 서비스 역할과 보안 정의 RPC만 쓰기 가능
- 낙관적 잠금으로 다른 운영자의 변경 덮어쓰기 방지
- 저장, 검토, 발행, 중지, 보관, 복원, 순서 변경, 롤백을 감사 로그에 기록
- 중요한 채점·결과 의미 변경은 작성자와 게시자를 분리하는 승인 확장 지점 유지

## 10. 삭제와 복구

운영 UI의 `삭제`는 `보관`으로 표현하고 다음 영향을 사전 표시한다.

- 홈·카탈로그 신규 노출 제거
- 신규 시작 차단
- 기존 진행 회차·완료 결과·함께하기 방 유지
- slug 재사용 금지
- 감사 로그와 릴리스 영구 보존

영구 삭제는 일반 화면에서 제공하지 않는다. 미게시·미참조 운영자 초안의 정리는 별도 최고관리자 유지보수 절차로 제한한다.

## 11. 검수 Gate

### 구현 완료 감사 — 2026-08-03

- 기본 콘텐츠 33개를 코어 2개, 주제 19개, 별난 연구 3개, 밸런스 팩 8개, 친구 게임 1개로 전수 확인했다.
- 기본 정보에서 바꾼 제목·설명·예상 시간은 실행 payload에도 동시에 반영하고, 서버가 둘의 불일치를 발행 차단한다.
- 주제 문항은 실제 뉴앙 영역·세부 성향과 결과 척도를 전용 선택 필드로 연결한다.
- 주제 결과는 점수 구간별 핵심 설명뿐 아니라 강점·주의점·바로 해볼 행동을 편집하며, 발행본과 완료 당시 결과 스냅샷에 함께 고정한다.
- 주제 검사는 완료 당시 검사 표지와 전체 문항까지 결과에 동결한다. 따라서 운영자가 문항을 고치거나 새 주제를 추가해도 과거 결과·다른 기기 복원·공개 프로필은 당시 표현으로 열린다.
- 별난 연구는 결과 유형 추가·제외, 보기별 결과 연결, 강점·주의점·관계 팁·작은 실험을 함께 관리한다. 완료 결과에는 당시 검사 전체와 선택된 결과 유형을 함께 동결해 과거 결과가 최신 편집본에 끌려가지 않게 했다.
- 밸런스 팩은 문항·보기·관계 대상·대화 깊이·민감도·점수 포함 여부와 그룹 지원 계산 방식을 관리한다. 현재 그룹 엔진이 완결되지 않은 `reciprocal_fit`, `discovery_only` 신규 발행은 자동 차단한다.
- 밸런스 방은 템플릿 버전뿐 아니라 실제 출제 순서인 세션 레시피도 게시 후 불변으로 유지한다.
- 친구 성향 맞히기는 운영자가 추가한 별도 slug도 초대 URL과 과거 릴리스 재현까지 같은 경로로 동작한다. `예상·선택 모두 일치`, `예상만 일치`, `선택만 일치`, `모두 다름`의 네 결과와 만료·잘못된 초대 안내까지 운영자가 관리한다.
- 코어 결과 리포트의 32개 코드 해석·근거 자료는 기존 `성향 콘텐츠` 원장을 정본으로 유지하고 검사 스튜디오에서 해당 관리 화면으로 연결한다. 같은 문구를 두 원장에 중복 저장하지 않는다.
- 삭제는 참조 무결성을 지키는 안전 보관으로 구현했다. 신규 노출과 시작은 막되 과거 결과·진행 회차·공유 링크는 유지한다.

`202608030005_assessment_content_operations.sql` 적용 후 실DB에서 저장→검토→반려→게시→중지→보관→복원→재게시→롤백을 수행했다. 핵심 생명주기 17개 검사는 통과했지만, 정렬 감사 로그에 대상 ID가 남지 않는 결함을 발견해 `202608030006_assessment_content_reorder_audit.sql`로 보완했다. 006 적용 후 기존 보관된 인수 기록을 복원해 정렬→재보관하고 대상 ID·전체 정렬 목록이 감사 로그에 남는지 확인하면 마지막 Gate가 닫힌다.

### 운영 적용 순서

1. Supabase SQL Editor에서 `supabase/migrations/202608030005_assessment_content_operations.sql`과 후속 보완인 `supabase/migrations/202608030006_assessment_content_reorder_audit.sql`을 번호 순서대로 각각 한 번 실행한다.
2. 로컬 또는 운영 관리자 계정으로 `/admin/experiences`를 연다.
3. 기존 검사 하나를 선택해 `작업본 저장`으로 운영 원장에 등록한다.
4. 제목이나 안내 문구를 작게 바꾸고 변경 사유를 적어 저장한다.
5. `검토 요청` 후 자동 검증의 차단 항목이 없는지 확인하고 게시한다.
6. 앱의 홈·검사 시작·결과 화면이 같은 문구를 사용하는지 확인한다.
7. 해당 검사를 잠시 중지해 신규 시작은 막히고 기존 결과는 열리는지 확인한 뒤 복원한다.
8. 직전 릴리스로 롤백하고 신규 진입에만 이전 버전이 적용되는지 확인한다.

이 실DB 점검까지 통과하면 단계 F의 마지막 항목을 완료로 바꾼다. 반복 인수는 `node scripts/smoke-assessment-studio-rest.mjs`로 수행한다. 고정 검수 기록은 종료 시 `보관됨` 상태가 되어 고객에게 노출되지 않는다. 실패 시 재게시로 덮지 말고 오류 시각·검사 slug·수행 동작을 기록해 감사 로그와 함께 원인을 확인한다.

## 14. 최종 수용 기준

- 기존 모든 검사·팩·문항이 누락 없이 검색된다.
- 유형별로 새 검사를 만들고 모든 고객 문구와 문항을 구조화된 폼에서 관리할 수 있다.
- 발행 차단 오류가 있는 작업본은 게시할 수 없다.
- 게시 후 홈, 시작, 채점, 결과, 공유가 같은 릴리스를 사용한다.
- 일시 중지 시 신규 시작만 차단되고 과거 결과는 열린다.
- 진행 중인 검사와 방은 생성 당시 버전으로 끝까지 동작한다.
- 동시에 편집한 변경을 조용히 덮어쓰지 않는다.
- 모든 중요 변경이 운영자·사유·시각과 함께 추적된다.
- 모바일 운영 화면에서 가로 스크롤이나 잘린 주요 동작이 없다.
- DB 기능이 아직 설치되지 않았거나 장애여도 기본 콘텐츠 조회와 고객 서비스가 중단되지 않는다.
