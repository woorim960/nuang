# 뉴앙 함께하기 밸런스 게임 모바일 UI/UX 개편 기준

- 문서 상태: 구현·검증 완료
- 작성일: 2026-07-31
- 적용 경로: `/assessments/together/balance-game/**`
- 상위 제품 기준: `NUANG_TOGETHER_BALANCE_GAME_PRODUCT_SPEC.md`
- 목표: 기존 뉴앙 커뮤니티·마이와 같은 제품군으로 느껴지면서, 고르는 순간만큼은 빠르고 몰입감 있는 함께하기 게임 경험을 만든다.

## 1. 개편 목표

1. 360~430px 모바일에서 가로 스크롤, 잘림, 겹침 없이 핵심 기능을 사용할 수 있어야 한다.
2. 커뮤니티·마이의 시각 언어를 따른다.
3. 문항 화면은 좌우 선택 영역을 정확히 50:50으로 나누고, 어느 곳을 눌러도 선택 즉시 다음 문항을 보여준다.
4. 방 생성부터 초대, 답변, 대기, 그룹 결과, 1:1 결과까지 한 흐름으로 이해되어야 한다.
5. 빠른 조작이 응답 중복, 선택 유실, 완료 실패로 이어지지 않아야 한다.
6. 화려한 장식보다 질문, 참여 상태, 결과의 재미가 먼저 보여야 한다.

### 비목표

- 채점 공식, 문항 콘텐츠, DB 스키마를 변경하지 않는다.
- 소규모 방을 무제한 공개 게임으로 확장하지 않는다.
- 밸런스 게임에 별도 디자인 시스템이나 하단 내비게이션을 만들지 않는다.

## 2. 뉴앙 디자인 DNA

커뮤니티·마이에서 공통으로 확인한 규칙을 밸런스 게임의 기준으로 사용한다.

| 항목      | 기준                                                 |
| --------- | ---------------------------------------------------- |
| 콘텐츠 폭 | 모바일 우선, 최대 430px 단일 컬럼                    |
| 배경      | 흰 surface 중심, 섹션 사이는 앱 배경색 8px 구분      |
| 헤더      | 56~58px, 1px 하단선, 반투명 흰색과 약한 blur         |
| 좌우 여백 | 기본 16px 내외의 `--nu-page-gutter`                  |
| 모서리    | 입력·버튼 12~15px, 강조 블록 최대 16px               |
| 색        | 본문은 neutral, 브랜드 보라는 CTA·현재 선택에만 사용 |
| 그림자    | 꼭 필요한 떠 있는 패널에만 약하게 사용               |
| 글자      | Pretendard, 본문 13~~16px, 화면 제목 19~~25px        |
| 터치      | 모든 조작 영역 최소 44×44px                          |

다음 표현은 줄인다.

- 팩마다 달라지는 강한 다색 그라데이션
- 모든 정보를 20px 카드에 가두는 구성
- 같은 CTA의 헤더·본문 중복
- 장식용 아이콘과 배지의 과다 사용
- 긴 설명을 첫 화면에 모두 노출하는 구성

## 3. 전체 사용자 흐름

```text
밸런스 게임 진입
→ 추천/전체 주제 탐색 또는 코드 입장
→ 주제 선택
→ 핵심 설정으로 방 만들기
→ 초대 또는 내 선택 시작
→ 좌우 50:50 연속 선택
→ 마지막 선택 자동 완료
→ 다른 참여자 대기 또는 결과
→ 그룹 핵심 결과
→ 한 사람 선택해 1:1 상세
→ 공유 또는 다른 주제로 다시 하기
```

### 흐름 원칙

- 한 화면에는 하나의 주 행동만 강하게 보인다.
- 초대 화면의 주 행동은 `초대 링크 보내기`, 답변 화면의 주 행동은 좌우 선택, 결과 화면의 주 행동은 `한 명씩 비교`다.
- 부가 기능인 코드 복사, QR, 계산 근거, 참여자 관리는 한 단계 낮은 위계로 둔다.
- 8문항 게임에는 중간 체크포인트를 넣지 않는다.
- 16·24문항의 라운드 경계도 별도 전면 화면으로 흐름을 끊지 않고, 짧은 진행 문구로만 알린다.

## 4. 화면별 설계

### 4.1 주제 선택 랜딩

구조:

1. 한 문장 소개
2. 컴팩트한 참여 코드 입력
3. 추천 주제
4. 분류 필터와 전체 주제
5. 접을 수 있는 함께하는 방법

규칙:

- 히어로는 화면을 크게 차지하는 그래픽 카드가 아니라 흰 배경의 짧은 소개 블록으로 만든다.
- `산 VS 바다` 예시는 작은 미리보기 한 줄로만 사용한다.
- 팩 카드는 커뮤니티 목록처럼 평면적인 흰 행을 사용한다.
- 팩별 고유 색은 작은 분류 라벨이나 미리보기 배경에만 제한한다.
- 카드 전체가 터치 영역이며 제목, 한 줄 설명, 대표 선택, 문항 수를 한 번에 훑을 수 있어야 한다.

### 4.2 방 만들기

바텀시트의 기본 노출 순서:

1. 선택한 주제
2. 방장 닉네임
3. 인원 2~8명
4. 게임 길이
5. 초대 방식
6. 고정 CTA

방 이름은 선택 항목으로 두되 핵심 설정보다 낮은 위계로 둔다. 각 설정은 중첩 카드 대신 구분선이 있는 섹션으로 표현한다. 하단 CTA는 safe area를 포함하고 키보드가 열렸을 때 입력을 가리지 않아야 한다.

### 4.3 방 준비·초대

- 상단에는 방이 준비됐다는 상태, 주제, 인원, 예상 시간만 표시한다.
- `초대 링크 보내기`를 전체 너비 주 CTA로 둔다.
- `코드 복사`, `링크 복사`, `QR`은 같은 줄의 보조 동작으로 둔다.
- `내 선택 시작하기`는 초대 CTA와 시각적으로 경쟁하지 않도록 별도 하단 섹션에 둔다.
- 참여자 목록은 닉네임보다 `완료`, `선택 중`, `자리 확인 중` 상태가 빠르게 보이게 한다.

### 4.4 문항 선택 화면

#### 레이아웃

```text
safe area
56px 헤더: 닫기 | 팩 이름 | 현재/전체
4px 진행률
112~144px 질문 영역: 라운드/진행 문구 + 질문
남은 높이 전체: 왼쪽 50% | 오른쪽 50%
safe area
```

- 러너는 `100dvh` 안에서 동작한다.
- 선택 영역은 러너의 남은 너비를 `repeat(2, minmax(0, 1fr))`로 정확히 나눈다.
- 좌우 사이에는 1px 구분선만 두고 gap, 바깥 카드 radius, 그림자를 사용하지 않는다.
- 중앙 `VS`는 구분선 위 36px 원형 배지로 겹쳐 둔다.
- 각 선택지는 남은 세로 공간 전체가 버튼이다.
- 선택 문구는 가운데 정렬, 18~22px, 굵기 700 이상, 최대 4줄을 수용한다.
- 매우 작은 높이에서는 질문 영역을 줄이고 선택 영역의 최소 높이를 우선 보장한다.
- 하단 이전/다음 footer는 제거한다.
- 이전 선택 수정은 헤더의 명확한 `이전 선택` 동작으로 제공하고, 방 나가기는 별도 닫기 동작으로 구분한다.

#### 선택 피드백

1. `pointerdown/keydown`에서 눌림 피드백을 즉시 보여준다.
2. 탭한 쪽에 90~120ms 동안 브랜드 tint와 체크를 표시한다.
3. 150~220ms 안에 다음 문항으로 전환한다.
4. 네트워크 저장은 직렬 처리하되 화면 전환을 막지 않는다.
5. 같은 질문의 좌·우 연타와 반복 Enter는 첫 선택 한 번만 인정한다.

#### 저장 상태기

```text
loading
→ ready(question)
→ submitting(choice locked)
→ saved(feedback)
→ advancing
→ ready(next)

failure
→ failed(current question + retry)

last answer
→ completing
→ waiting | result

removed | closed | expired
→ terminal recovery screen
```

구현 안전 규칙:

- 질문 ID 기준 요청 잠금을 사용한다. React 렌더 상태만으로 중복 탭을 막지 않는다.
- 저장 응답이 요청한 질문과 현재 참여 세션에 해당하는지 확인한다.
- 저장 실패 시 실패한 문항으로 돌아오고, 사용자가 골랐던 선택을 복원한 채 한국어 재시도 안내를 표시한다.
- 마지막 응답 저장과 방 완료 호출을 분리한다. 완료만 실패한 경우 답을 다시 고르게 하지 않고 `결과 다시 준비하기`를 제공한다.
- 재진입 시 서버에 저장된 첫 미응답 문항부터 정확히 이어간다.
- 백그라운드 복귀, 다른 탭, 방장 내보내기·마감 상태도 다음 요청 전후에 안전하게 반영한다.

#### 접근성

- 두 선택 버튼을 질문을 이름으로 가진 group으로 묶는다.
- 버튼의 접근 가능한 이름은 실제 선택지 문구를 사용한다. 시각적 좌·우 위치만 이름으로 쓰지 않는다.
- `aria-pressed`와 진행 상태를 제공하되 질문 heading focus와 live region의 중복 낭독을 피한다.
- 키보드 Tab, Enter, Space로 고를 수 있고 이전 선택 동작에 접근할 수 있어야 한다.
- `prefers-reduced-motion`에서는 화면 이동을 즉시 전환하고 scale 애니메이션을 제거한다.
- 200% 텍스트 확대에서도 선택 문구가 잘리거나 겹치지 않아야 한다.

### 4.5 대기 화면

- 완료 아이콘, `내 선택 완료`, 필요한 남은 사람 수를 첫 블록에 표시한다.
- 참여자 진행 상태를 바로 이어 보여준다.
- 초대 링크를 주 CTA로 반복 제공한다.
- polling 중에도 화면 전체를 깜빡이지 않고 참여자 행과 결과 진입 상태만 갱신한다.

### 4.6 그룹 결과

정보 순서:

1. 그룹 점수와 한 줄 결과
2. 다 같이 통한 선택 TOP
3. 재미있게 갈린 선택 TOP
4. 한 명씩 비교
5. 다른 주제로 다시 하기 / 공유
6. 계산 근거·참여자 관리·마감 보조 영역

규칙:

- 점수는 핵심이지만 화면 전체를 차지하는 장식형 히어로로 만들지 않는다.
- 결과 공유 CTA는 한 곳에만 강하게 둔다.
- `현재 결과`는 이후 바뀔 수 있음을 작은 상태 문구로 표시한다.
- 상세 질문 목록은 한 화면에 모두 펼치지 않고 필요한 항목만 확장한다.

### 4.7 1:1 결과

- 상대와 나의 점수, 같은 선택 수를 첫 블록에 표시한다.
- `전체 / 같은 선택 / 다른 선택` 필터는 커뮤니티 탭과 같은 얇은 underline 또는 절제된 pill을 사용한다.
- 다른 선택은 `나`와 `상대`의 답을 좌우 고정 열로 표시해 행마다 너비가 흔들리지 않게 한다.
- 뒤로가기는 그룹 결과로 돌아가며 방 목록으로 나가지 않는다.

## 5. 반응형 기준

필수 검증 viewport:

- 360×568
- 360×667
- 390×664
- 390×844
- 430×740
- 768px 이상 중앙 430px 쉘

수용 조건:

- 어떤 화면도 가로 스크롤이 생기지 않는다.
- 문항 화면에서 선택 버튼이 질문이나 safe area에 가려지지 않는다.
- 긴 선택지 4줄, 긴 방 이름, 8명 닉네임 목록을 수용한다.
- 모바일 키보드가 열린 방 생성·참여 폼에서 현재 입력과 CTA에 접근할 수 있다.

## 6. 성능·신뢰성 기준

- 선택 입력 피드백: 100ms 이내
- 다음 문항 표시: p95 250ms 이내
- 질문당 동시 저장 요청: 최대 1개
- 1.5초 네트워크에서도 다음 문항 화면은 먼저 표시
- 저장 실패 시 선택 유실 0건, 현재 문항 복구
- 재진입 시 마지막 저장 지점과 불일치 0건
- 빠른 좌→우 연타, 반복 Enter에서 서버 저장 1건

## 8. 최종 검수 시나리오

1. 2명·8문항 방을 만들고 초대 링크를 보낸다.
2. 360px 화면에서 좌·우 선택 영역이 정확히 같은 너비인지 확인한다.
3. 첫 선택 후 별도 다음 버튼 없이 다음 문항으로 이동하는지 확인한다.
4. 좌우를 10ms 간격으로 연타해 한 선택만 저장되는지 확인한다.
5. 이전 선택으로 돌아가 저장값이 표시되고 수정 후 다시 진행되는지 확인한다.
6. 저장 실패를 발생시켜 실패 문항과 선택이 복원되는지 확인한다.
7. 마지막 문항 저장 성공·완료 실패를 분리해 복구할 수 있는지 확인한다.
8. 8문항 중간에 체크포인트가 나오지 않는지 확인한다.
9. 대기에서 두 번째 참여자가 완료하면 결과로 자연스럽게 전환되는지 확인한다.
10. 그룹 결과에서 상대를 눌러 1:1 결과를 보고 정확히 그룹 결과로 돌아오는지 확인한다.
11. 8명 방, 긴 닉네임, 긴 문항, 200% 확대, 키보드만으로 같은 흐름을 점검한다.

- 실제 2명·8문항 비공개 방에서 생성, 초대, 연속 선택, 대기, 자동 결과 전환, 그룹 결과, 1:1 비교 흐름을 검증했다.
- 360×568 문항 화면에서 좌우 선택 영역이 각각 동일한 너비와 높이를 사용하고 가로 스크롤이 생기지 않는 것을 확인했다.
- 390×844 결과 화면에서 다른 선택의 두 답변 열이 같은 너비를 유지하고 화면 밖으로 넘치지 않는 것을 확인했다.
- 느린 저장 중에도 다음 문항이 먼저 보이며, 좌·우 연타는 첫 선택만 저장하고, 저장·완료 실패는 각각 안전하게 재시도하도록 자동 테스트를 보강했다.
- `346`개 테스트 파일의 `1,572`개 테스트, TypeScript 검사, Prettier 검사, ESLint, Next.js 운영 빌드를 통과했다. ESLint에는 이번 작업과 무관한 기존 경고 3건만 남아 있다.
- 200% 확대처럼 가로 폭이 280px 미만이 되는 극단 조건에서는 두 선택지를 세로로 재배치해 문구의 가독성과 터치 영역을 우선 보장한다.
