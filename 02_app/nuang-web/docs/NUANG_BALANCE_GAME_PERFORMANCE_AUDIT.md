## 2. 확인된 병목

### 서버와 데이터베이스의 물리적 거리

Vercel 함수는 기본 리전인 미국 `iad1`에서, Supabase 데이터베이스는 서울에서 실행되고 있었다. 짧은 쿼리도 매번 대륙 간 왕복 지연을 부담하고, 한 요청 안에서 쿼리를 순차 실행할수록 지연이 누적됐다.

### 방 생성

- 두 개의 rate limit RPC를 순차 실행했다.
- 방을 만들 때마다 팩 템플릿·버전·레시피를 다시 동기화했다.
- 각 라운드와 선택지를 반복문 안에서 조회·삽입·검증했다.
- 생성 직후 완전한 방 상태를 다시 여러 쿼리로 읽었다.

### 참여

- API route와 서버 함수가 참여 미리보기를 중복 조회했다.
- 제목과 설명만 필요한 미리보기에 전체 문항 팩을 로드했다.
- 참여 예약·확정 전후로 여러 쿼리를 순차 실행했다.

### 문항 응답

응답 한 번에 방, 참여자, 활동 시각, 팩 버전, 템플릿, 전체 문항, 현재 선택지, 라운드를 각각 확인한 뒤 저장 RPC를 호출했다. 클라이언트는 저장을 직렬화하므로 마지막 문항에서 이전 저장 작업까지 기다리는 문제가 커졌다.

### 완료와 결과 이동

- 참여자 권한 확인, 완료 라운드 조회, 누락 라운드별 완료 RPC, 게임 완료 RPC를 순서대로 실행했다.
- 완료 응답에는 결과 화면에 필요한 상태가 없어 경로 이동 뒤 다시 전체 상태를 조회했다.
- 상태 polling에서도 불변 문항 팩을 반복 조회하고 매번 활동 시각 쓰기를 기다렸다.

### 인덱스

방별 라운드 선택지와 참여자별 라운드 완료 여부를 읽는 핵심 경로에 맞는 복합 인덱스가 없었다.

## 3. 적용한 개선

### 실행 리전 최적화

Vercel 함수를 서울 `icn1`으로 고정해 운영 데이터베이스와 같은 지역에서 실행하도록 했다.

### 데이터베이스 왕복 통합

- `save_response_by_item_key`: 문항 식별, 권한 확인, 라운드 확인, 멱등 저장을 하나의 트랜잭션으로 통합했다.
- `complete_participant_game`: 누락 라운드 완료와 참여자 게임 완료를 하나의 트랜잭션으로 통합했다.
- 참여 미리보기에 팩 제목과 설명 스냅샷을 포함해 전체 팩 로드를 제거했다.
- 새 RPC는 `service_role`에만 실행 권한을 부여했다.

### 생성 알고리즘 개선

- 독립 rate limit 검사를 병렬화했다.
- 동일 릴리스의 팩 동기화와 불변 팩 로딩을 warm process에서 재사용한다.
- 라운드를 한 번에 upsert하고, 누락된 선택지만 한 번에 insert하도록 바꿨다.
- 문항 수가 8/12/24로 늘어도 네트워크 왕복 횟수가 선형으로 증가하지 않는다.

### 상태 조회와 화면 전환 개선

- 라운드 선택지, 참여자, 응답 조회를 병렬화했다.
- 참여자 활동 시각 갱신을 30초 단위로 제한했다.
- 생성·참여·완료 결과의 방 상태를 메모리에 캐시해 다음 화면의 첫 렌더에 즉시 사용한다.
- 완료 API가 전체 결과 상태를 함께 반환해 마지막 문항 직후 결과 화면을 바로 그린다.
- 대기 상태 polling은 화면 상태에 따라 1.5~3초로 조정하고, 화면 활성화 시 즉시 갱신한다.

### 인덱스 추가

- `round_item(room_id, round_id, display_order)`
- `round_completion(room_id, participant_id, round_id)`

## 7. 운영 관찰 권장 사항

- cold start가 포함된 첫 방 생성은 warm 상태보다 느릴 수 있으므로 Vercel 함수 실행 시간과 cold start 비율을 계속 관찰한다.
- 결과 스냅샷 생성은 마지막 참여자 완료 요청에 포함된다. 문항·참여 인원 상한이 커지면 p95를 기준으로 비동기화 여부를 재검토한다.
- 운영 성능 회귀 기준은 방 생성 p95 2초, 방 참여 p95 1초, 응답 저장 p95 500ms, 완료 p95 1.5초로 둔다.
