# 뉴앙 코어·정밀 검사 기기 간 저장·이어하기·재검사 통합 기획

- 문서 상태: 구현 기준선
- 작성일: 2026-08-02
- 적용 범위: 첫 성향 검사(`nu-core-quick`), 정밀 성향 검사(`nu-core-full`)
- 목표: 비로그인 즉시 시작의 장점을 유지하면서, 로그인 후에는 어느 기기에서든 정확한 화면부터 이어하고 모든 완료 결과를 다시 볼 수 있게 한다.

## 1. 제품 결론

뉴앙 검사는 다음 원칙으로 동작한다.

1. 비로그인 사용자는 별도 절차 없이 바로 시작한다. 답과 현재 위치는 먼저 기기에 저장한다.
2. 로그인 사용자는 기기 저장 성공을 기다린 뒤 화면을 즉시 진행하고, 같은 기록을 계정에도 백그라운드 저장한다.
3. 로그인 직후 해당 기기에 남아 있던 검사 기록과 계정 기록을 병합한다. 성공을 확인하기 전에는 기기 원본을 지우지 않는다.
4. 다른 기기에서는 계정에 저장된 진행 기록을 내려받아 질문, 중간 쉼표, 추가 확인 안내, 추가 질문 중 정확한 화면을 복원한다.
5. 완료 결과는 수정하지 않는 과거 기록이다. 다시 검사는 기존 결과를 덮어쓰거나 삭제하지 않고 새 회차를 만든다.
6. 고객에게 DB, 로컬, 서버, revision 같은 내부 용어를 노출하지 않는다. 필요한 순간에만 “다른 기기에서도 이어볼 수 있어요”처럼 결과 중심으로 안내한다.

## 2. 현행 진단

현재 IndexedDB `nuang-local/assessmentAttempts`에는 응답, 현재 인덱스, 중간 체크포인트, 추가 확인 상태, 완료 결과가 저장된다. 그러나 로그인 여부와 무관하게 진행 상태는 한 기기에만 남는다. 서버 저장은 완료 결과 화면을 연 뒤 `/api/claim-result`가 실행될 때만 발생한다.

따라서 현재는 다음 문제가 있다.

- 로그인해도 진행 중 검사가 DB에 저장되지 않는다.
- 로그인 콜백은 계정·동의·프로필만 만들고 브라우저 기록을 가져오지 않는다.
- 다른 기기의 홈은 완료 결과만 읽고 진행 중 위치를 알 수 없다.
- 홈 진행률이 응답 수와 현재 화면 위치를 구분하지 못하고, 추가 확인 문항이 있으면 100%를 넘을 수 있다.
- 정밀 결과가 있으면 정밀 검사 진입 시 곧바로 이전 결과로 이동해 “처음부터 다시” 의도를 수행하기 어렵다.
- 계정에서 내려받은 기록을 로그아웃 뒤 같은 브라우저의 다른 계정에 보여주지 않도록 소유 범위를 분리해야 한다.

## 3. 사용자 여정

### 3.1 처음 시작

- 제목: `3분이면 내 성향의 첫 단서를 만나요`
- 주 행동: `첫 성향 검사 시작하기`
- 비로그인 보조 안내: `로그인하면 다른 기기에서도 이어볼 수 있어요.`

### 3.2 질문에서 이어하기

- 제목: `{N}번부터 이어가요`
- 정보: `{answered}개 답변 완료 · 약 {minutes}분 남음`
- 주 행동: `{N}번부터 이어하기`
- 진행률은 `유효하게 답한 실행 문항 수 / 현재 실행 문항 수`로 계산한다.
- 현재 인덱스와 답변 수가 다를 수 있으므로 둘을 같은 값으로 취급하지 않는다.

### 3.3 특수 화면 복원

- 중간 체크포인트: `중간 쉼표부터 이어가요` / `계속 이어하기`
- 추가 확인 안내: `마지막 확인 질문을 이어가요` / `확인 질문 이어가기`
- 추가 확인 질문: `확인 질문 {N}번부터 이어가요`
- 결과 준비 중: `답변은 모두 끝났어요` / `결과 준비 이어가기`

복원 기준은 퍼센트가 아니라 저장된 `currentIndex`, `milestones`, `adaptiveStatus`, `completionStatus`다.

### 3.4 다른 기기에서 복원

- 홈을 열 때 로그인 계정의 진행 기록을 먼저 내려받아 기기 캐시와 병합한다.
- 다른 기기의 기록을 실제로 채택한 경우 한 번만 `다른 기기에서 답하던 {N}번부터 불러왔어요`라고 알린다.
- 네트워크가 끊겨도 기기 저장이 성공하면 검사를 계속한다.
- 계정 저장 실패는 비차단 안내로 처리하고 다음 진입 또는 다음 저장 때 다시 시도한다.

### 3.5 완료 후 다시 검사

완료 카드와 공통 결과 리포트에서 다시 검사 경로를 제공한다.

- 시트 제목: `새 결과를 만들어볼까요?`
- 설명: `이전 결과는 내 기록에 그대로 남고, 이번 답으로 새 리포트가 만들어져요.`
- 주 행동: `처음부터 다시 검사하기`
- 보조 행동: `취소`

진행 중 회차가 있을 때는 다음처럼 바꾼다.

- 제목: `답하던 검사가 있어요`
- 설명: `현재 답한 내용부터 이어가거나, 이 회차만 정리하고 처음부터 시작할 수 있어요. 완료한 이전 결과는 삭제되지 않아요.`
- 주 행동: `{N}번부터 이어하기`
- 보조 행동: `현재 답을 정리하고 처음부터`

“처음부터”는 이전 빠른 검사 응답 자동 재사용을 포함하지 않는다.

## 4. 데이터 정본과 보안 경계

### 4.1 정본

- 비로그인: IndexedDB가 정본이다.
- 로그인: 계정 DB가 정본이고 IndexedDB는 즉시 반응과 오프라인 복원을 위한 캐시다.
- 모든 답은 IndexedDB에 먼저 저장한 후 계정 DB로 비동기 전송한다.
- 완료 결과는 기존 서버 재검증·재채점·원자 저장 경로를 유지한다.

### 4.2 진행 스냅샷

기존 완료용 `assessment.assessment_attempt`와 충돌하지 않도록 계정 진행 전용 테이블을 둔다. 완료 결과 귀속 RPC는 같은 `local_result_id`를 이미 가진 미완료 attempt를 허용하지 않기 때문이다.

`assessment.account_assessment_progress` 필수 필드:

- 계정과 클라이언트 attempt 식별자
- 검사 slug, 종류, release
- 상태: `in_progress`, `completed` (같은 검사·릴리스의 이전 초안은 조회 단계에서 최신 회차만 노출)
- 서버 revision
- 검증된 전체 진행 snapshot
- 클라이언트 활동 시각과 서버 갱신 시각
- 완료·대체 시각

진행 snapshot은 서버 전용 API가 검사 정의와 다음 조건을 검증한 뒤에만 쓴다.

- 알려진 코어/정밀 검사와 현재 허용 release인가
- 기본 문항 순서가 공식 정의와 정확히 같은가
- 추가 문항은 해당 검사 정의에 존재하는가
- 응답 item ID가 중복되지 않고 허용 집합 안에 있는가
- 일반 응답은 1~5, `판단 어려움` 응답은 값 없이 허용 사유를 가지는가
- 현재 인덱스와 상태가 실행 문항 범위를 벗어나지 않는가

브라우저는 assessment 스키마에 직접 쓰지 않는다. 인증 확인 뒤 service role로 동작하는 Route Handler만 쓰며, 원 응답을 로그·분석 이벤트·오류 payload에 포함하지 않는다.

### 4.3 계정 분리

- 서버에서 내려받거나 서버 저장이 확인된 기기 캐시는 `ownerAccountId`로 소유 범위를 기록한다.
- 로그인 병합 시 현재 계정과 다른 소유 범위의 캐시는 채택하지 않는다.
- 로그아웃 시 계정 소유 진행 캐시를 기기에서 제거한다. 계정 DB 기록은 유지된다.
- 아직 어느 계정에도 귀속되지 않은 guest 기록만 다음 로그인에서 가져올 수 있다.

## 5. 동기화 계약

### 5.1 진입 동기화

홈, 코어 검사 runner, 정밀 검사 intro, 내 검사 기록 진입에서 공통 조정기를 실행한다.

1. 기기에서 유효한 guest/현재 계정 진행 기록을 읽는다.
2. 로그인 여부를 확인한다.
3. 로그인이라면 기기 변경분을 배치 업로드한다.
4. 계정의 진행 스냅샷을 내려받는다.
5. 같은 attempt ID는 revision과 상태를 기준으로 하나를 선택한다.
6. 다른 기기의 더 최신 계정 snapshot을 IndexedDB에 저장한다.
7. 완료 결과는 `/api/account-results`와 합쳐 중복 없이 표시한다.

### 5.2 실행 중 동기화

- 답 선택, 다음/이전 이동, 중간 체크포인트, 추가 확인 전환, 완료 상태 변화마다 저장 큐에 최신 snapshot 한 개만 남긴다.
- 같은 attempt의 요청은 직렬화해 revision 역전을 막는다.
- 401은 비로그인 정상 상태로 취급하고 세션 동안 반복 요청하지 않는다.
- 409 충돌은 서버 snapshot을 보존하고, 자동으로 안전하게 고를 수 없으면 사용자 선택 대상으로 남긴다.
- 페이지 이동을 막지 않는다.

### 5.3 선택 기준

동일 attempt ID라면 완료 상태가 진행 상태보다 우선한다. 같은 상태라면 서버 revision, 응답 완전성, 마지막 활동 순으로 비교한다. 서로 다른 active attempt의 답은 자동으로 섞지 않는다. 대표 회차는 마지막 활동이 가장 최근인 것으로 고르되 나머지는 즉시 삭제하지 않는다.

## 6. 홈 단일 상태 모델

실제 홈은 `AssessmentHomeCoreSection` 하나만 사용한다. 구형 `HomeDashboard`의 별도 판단 로직을 새 기능에 연결하지 않는다.

상태 우선순위:

1. 진행 중 정밀 검사
2. 진행 중 첫 검사
3. 최근 정밀 완료 결과
4. 최근 첫 검사 완료 결과
5. 기록 없음

홈 카드의 주 행동은 항상 하나, 보조 행동은 최대 하나다.

- 진행 중: 주 행동 `정확한 위치부터 이어하기`, 보조 행동 `처음부터 다시`
- 정밀 완료: 주 행동 `내 성향 결과 보기`, 보조 행동 `정밀 검사 다시하기`
- 첫 검사 완료: 주 행동 `정밀 검사 시작하기`; 첫 검사 재검사는 결과 리포트에서 제공

진행률은 0~100으로 제한하고, 접근성 문구는 `60개 중 18개 답변 완료, 19번부터 이어서 진행`처럼 답변 수와 현재 위치를 모두 읽는다.

## 7. UI 품질 기준

- 기존 질문 화면의 44px 이상 터치 영역, 저장 복구 overlay, bottom sheet focus trap, 220ms 질문 전환을 유지한다.
- 홈 hero만 radius 16px과 매우 옅은 brand surface를 사용한다. 중첩 카드·과한 glow·새 임의 색상은 만들지 않는다.
- 홈 CTA 높이 48px, 진행 bar 6px, 모바일 기준 320/360/390/430/520px에서 검증한다.
- 긴 한국어는 `word-break: keep-all`, 200% 확대에서 버튼·메타 정보가 겹치지 않아야 한다.
- 복구 알림은 `aria-live=polite`, 기기 저장 실패는 `assertive`로 구분한다.
- `prefers-reduced-motion`에서는 이동·폭 애니메이션을 제거한다.

## 8. 구현 순서와 점검 게이트

### Gate A — 기반

- DB migration, 인덱스, RLS, service role 권한
- 런타임 데이터 검증 계약
- 인증 API GET/PUT
- 완료 불변과 계정 분리 테스트

### Gate B — 저장소

- IndexedDB attempt에 계정·revision 동기화 메타 추가
- 로그인 병합 조정기
- runner의 모든 상태 전환에서 background sync
- 원격 실패 시 로컬 진행 보장

### Gate C — 정확한 재개

- 홈 진입 전 동기화
- 질문·중간 쉼표·추가 확인·결과 준비 화면 복원
- 다른 기기 복구 안내
- 진행률 100% 초과 방지

### Gate D — 재검사

- 새 attempt 강제 생성 command
- 홈 확인 sheet와 상태별 보조 행동
- 정밀 결과 redirect 우회
- 기존 결과 불변 확인

### Gate E — 기록과 검증

- 마이 기록에서 계정 active 진행 표시
- 로그아웃 계정 캐시 제거
- 단위·Route Handler·통합 테스트
- typecheck, lint, build, 모바일 시각 확인

## 9. 완료 수용 기준

1. 기기 A에서 정밀 검사 18개 응답 후 종료하고 기기 B에서 로그인하면 홈에 18/60과 19번 이어하기가 보인다.
2. CTA는 실제 19번째 질문을 연다.
3. 중간 체크포인트, 추가 확인 안내, 추가 확인 질문도 해당 화면으로 복원한다.
4. 로그인 직후 기존 guest 기록을 중복 없이 계정에 저장한다.
5. 계정 저장 실패에도 기기 저장이 성공하면 검사를 계속한다.
6. 연결이 복구되면 다음 진입 또는 저장에서 다시 전송한다.
7. 진행률은 추가 문항이 있어도 100%를 넘지 않는다.
8. 완료 후 다시 검사는 새 attempt와 새 결과를 만들고 이전 결과·공유 링크·비교 기록을 유지한다.
9. 진행 중 처음부터 다시는 명시적 확인 없이는 기존 초안을 대체하지 않는다.
10. 다른 계정의 진행 캐시가 홈·마이·runner에 표시되지 않는다.
11. 고객 화면에 DB·server·local·revision 용어가 보이지 않는다.
12. 원 응답이 공개 API, 분석 이벤트, 오류 로그에 노출되지 않는다.

## 10. 후속 확장

- 동일 검사에서 서로 다른 active 회차가 의미 있게 갈라진 경우의 복구 선택 sheet
- 문항 단위 revision과 두 기기 동시 수정 충돌 화면
- Safari private mode용 메모리 fallback
- 진행 복구율, 재검사 시작률, 동기화 실패율 운영 지표

P0 구현은 고객이 요청한 기기 간 진행·완료 이력·홈 정확한 이어하기·안전한 재검사를 완성하고, 동시 편집 충돌 UI는 데이터가 소실되지 않는 보존 구조를 먼저 마련한 뒤 P1에서 확장한다.

## 12. 2026-08-02 최종 경계 재감사

기획서의 12개 완료 수용 기준을 코드·DB·테스트에 다시 대조했다. 기본 여정은 구현돼 있었지만, 일반 성공 흐름 중심의 기존 테스트가 놓친 다섯 가지 경계 결함이 있어 아래와 같이 보완했다.
