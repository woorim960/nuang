# 뉴앙 선택 동의·운영센터 통합 기획서

- 문서 상태: 구현 기준 확정
- 기준일: 2026-08-03
- 대상: 로그인 화면의 두 선택 동의, 마이 설정, 서버 데이터 소비 지점, 운영센터
- 관련 화면: `/login`, `/my/settings/notifications`, `/admin/consents`

## 1. 목표

로그인 화면의 두 선택 항목이 단순 체크박스가 아니라 실제 기능과 연결되어야 한다.

1. `서비스 개선을 위한 이용 데이터 수집`
   - 동의한 회원의 최소한의 기능 이용 흐름만 수집한다.
   - 검사 답변, 뉴앙코드, 게시글 내용, 검색어, 동적 URL 식별자는 수집하지 않는다.
   - 동의하지 않거나 철회하면 선택형 이용 분석을 서버에서 즉시 차단한다.
2. `새로운 검사와 소식 알림`
   - 동의한 회원만 새 검사·이벤트·서비스 소식의 발송 가능 대상으로 분류한다.
   - 실제 외부 발송은 인증된 연락처가 있는 회원만 가능하다.
   - 동의하지 않아도 검사, 커뮤니티, 결과 리포트 등 모든 핵심 기능을 동일하게 이용한다.

필수 보안·장애 기록과 선택형 이용 분석은 서로 다른 데이터다. 서비스 보호에 필요한 최소 보안 기록은 선택 동의와 무관하게 처리하되, 선택형 제품 분석으로 전용하지 않는다.

## 2. 사용자에게 생기는 차이

| 선택 항목 | 동의한 경우 | 동의하지 않은 경우 |
|---|---|---|
| 이용 데이터 | 로그인 후 어떤 서비스 영역을 방문했는지 최소 이벤트를 저장하고 운영센터에서 집계한다. | 선택형 이용 이벤트를 저장하지 않는다. 서비스 이용에는 제한이 없다. |
| 새 검사·소식 | 발송 가능 대상이 된다. 인증된 연락처가 있으면 해당 채널의 발송 후보가 된다. | 광고성·홍보성 소식 대상에서 제외한다. 계정·보안·거래성 필수 안내는 그대로 받을 수 있다. |

로그인 화면에서 체크하지 않은 것은 기존 회원의 명시적 철회로 해석하지 않는다. 기존 동의 철회는 로그인 후 설정 화면에서 본인이 직접 실행한다.

## 3. 현행 구현 감사

### 3.1 구현되어 있는 부분

- 로그인 선택값 입력과 짧은 수명의 HttpOnly consent intent
- `consent.age_and_consent_status`의 현재 플래그
- `consent.consent_record`의 동의 변경 이력 기반
- 마이의 마케팅 설정 화면
- 인증 연락처의 암호화 저장과 마스킹 출력
- 운영센터의 서버 전용 접근, 역할 계정, 감사 화면 기반

### 3.2 반드시 고쳐야 하는 결함

1. 로그인 callback은 현재 플래그를 갱신하지만 선택 동의 이력을 남기지 않는다.
2. 마이 설정은 마케팅 이력만 갱신하고 현재 플래그를 갱신하지 않는다.
3. 계정과 무관한 localStorage 선택값이 로그아웃 뒤에도 남아 다른 로그인에 재사용될 수 있다.
4. 재로그인에서 체크하지 않은 값을 기존 동의 철회로 덮어쓸 수 있다.
5. 현재값 갱신과 이력 삽입이 서로 다른 DB 요청이라 일부만 성공할 수 있다.
6. 주제검사 품질 관찰 전송 경로가 선택형 이용 데이터 동의를 서버에서 확인하지 않는다.
7. 마케팅 발송 가능 대상을 계산하는 단일 서버 계약이 없다.
8. `consent` 스키마에 과도하게 넓은 과거 grant가 남아 있다.
9. 마이에서 이용 데이터 동의를 조회·변경할 수 없다.
10. 운영센터에서 현재 동의율, 최근 변경, 발송 가능 대상, 수집 상태를 확인할 수 없다.

## 4. 단일 데이터 기준

### 4.1 원칙

- 이력 원장: `consent.consent_record`
- 빠른 현재값: `consent.age_and_consent_status`
- 모든 변경은 하나의 DB transaction/RPC에서 원장 추가와 현재값 갱신을 함께 수행한다.
- 읽기는 현재값을 사용하되, migration에서 원장과 현재값을 일치시키고 정기 무결성 검사를 제공한다.
- 같은 시각의 변경 순서는 `recorded_at desc, id desc`로 결정한다.

### 4.2 상태 전이

| 상황 | 처리 |
|---|---|
| 최초 계정 연결 + 체크 | `granted`, 현재값 `true` |
| 최초 계정 연결 + 미체크 | `revoked`, 현재값 `false` |
| 기존 회원 재로그인 + 미체크 | 기존값 유지 |
| 기존 회원 재로그인 + 체크 | 기존 `false`면 `granted`, 이미 `true`면 중복 기록하지 않음 |
| 마이 설정에서 켜기 | `granted`, 현재값 `true` |
| 마이 설정에서 끄기 | `revoked`, 현재값 `false`, 소비 지점 즉시 차단 |
| 동일 요청 재시도 | 같은 상태·버전이면 중복 이벤트를 만들지 않음 |

로그인 intent의 선택값은 `false=철회`가 아니라 `true=새 동의 요청`, `false=변경 요청 없음`으로 처리한다. 최초 연결에서만 false를 초기 미동의로 확정한다.

### 4.3 기록 필드

- `account_id`
- `consent_type`: `analytics` 또는 `marketing`
- `consent_version`
- `status`: `granted` 또는 `revoked`
- `source`: `account_gate`, `my_settings`, `legacy_backfill`, `account_merge`
- `recorded_at`, `revoked_at`
- 최소 metadata: surface, channel, migration version

IP, user-agent 원문, 이메일·전화번호, 검사 결과와 자유 텍스트는 동의 metadata에 넣지 않는다.

## 5. 로그인 UX

`선택 동의 보기`는 필수 동의와 시각적으로 분리하고 기본값은 꺼짐으로 둔다.

### 5.1 표시 문구

- `서비스 개선을 위한 이용 데이터 수집`
  - 설명: `어떤 화면과 기능을 이용했는지만 모아 더 편하게 개선해요. 검사 답변과 작성한 내용은 포함하지 않아요.`
- `새 검사·이벤트 소식 받기`
  - 설명: `새 검사와 함께하기, 이벤트 소식을 받을 수 있어요. 설정에서 언제든 바꿀 수 있어요.`

선택하지 않아도 로그인 버튼을 사용할 수 있고 불이익을 암시하는 표현을 쓰지 않는다.

## 6. 마이 설정 UX

화면 제목은 `데이터 및 알림`으로 바꾼다. 두 항목을 각각 독립 스위치로 제공한다.

- 최초 로딩 중에는 현재값을 추측하지 않는다.
- 변경 즉시 낙관적 UI를 보여주되 실패 시 원래 값으로 복구한다.
- 저장 중 중복 조작을 막는다.
- 성공: `이용 데이터 수집을 켰어요`, `새 검사와 소식을 받도록 설정했어요`
- 철회: `앞으로 선택형 이용 데이터를 저장하지 않아요`, `광고성 소식을 받지 않도록 설정했어요`
- 필수 안내와 선택 소식의 차이를 하단에 짧게 설명한다.

## 7. 이용 데이터 수집 계약

### 7.1 허용 이벤트

첫 릴리스는 `screen_view`만 수집한다. 서버가 다음과 같은 고정 서비스 영역으로 정규화한다.

- `home`
- `assessment`
- `result`
- `community`
- `trait_map`
- `my`
- `together`
- `settings`
- `other`

동적 ID, query, hash, 원문 pathname은 저장하지 않는다. 한 계정·영역의 짧은 시간 내 중복 이벤트는 DB에서 제한한다.

### 7.2 서버측 차단

클라이언트의 `consented=true` 같은 주장은 신뢰하지 않는다. API는 다음을 모두 확인한다.

1. 정상 로그인 회원
2. 활성 계정
3. canonical analytics 현재값 `true`
4. 허용 이벤트명과 영역
5. same-origin 요청

하나라도 실패하거나 DB 상태를 확인할 수 없으면 저장하지 않는다. 일반 화면 요청 자체는 실패시키지 않는다.

### 7.3 보관

- 원시 선택 이벤트: 기본 90일
- 개인을 직접 식별하지 않는 집계: 운영 필요 기간을 별도 정책으로 확정
- 철회: 신규 수집 즉시 중단
- 계정 삭제: FK cascade로 개인 연결 이벤트 삭제

정확한 보관기간과 국외 처리 안내는 개인정보 처리방침과 법무 검토에서 최종 확정한다.

## 8. 마케팅 대상 계약

운영 도구와 향후 발송기는 반드시 서버 전용 audience resolver만 사용한다.

대상 조건은 모두 만족해야 한다.

1. 계정 상태 `active`
2. canonical marketing 현재값 `true`
3. 최신 동의 버전 유효
4. 채널별 인증 연락처 존재
5. suppression/unsubscribe 없음
6. 계정 병합·충돌·삭제 처리 중이 아님

현재 릴리스의 운영센터는 대상 수와 채널 준비 상태까지만 제공한다. 대량 발송 버튼은 수신거부 링크, 발신자 표시, 발송 시간, 재확인 주기, suppression 및 outbox가 모두 준비되기 전 노출하지 않는다.

## 9. 운영센터 `/admin/consents`

### 9.1 상단 지표

- 전체 동의 상태를 가진 회원
- 이용 데이터 동의율
- 마케팅 동의율
- 인증 이메일이 있는 마케팅 대상
- 최근 7일 동의 변경
- 최근 24시간 저장된 선택 이벤트

분모와 집계 시각을 함께 표시한다. 데이터가 없으면 0으로 꾸미지 않고 `아직 집계할 데이터가 없습니다`로 표시한다.

### 9.2 최근 변경 목록

- 유형, 상태, 변경 시각, 출처, 버전
- 계정은 전체 UUID 대신 앞 8자리 참조만 표시
- 원문 이메일·전화번호·IP·암호문·자유 metadata는 표시하지 않음
- 유형과 상태 필터 제공

### 9.3 운영 원칙

- 운영자가 사용자를 대신해 동의를 켤 수 없다.
- 오류 정정이 필요하면 사용자 재동의 또는 별도 개인정보 처리 절차를 따른다.
- CSV 원문 연락처 내보내기는 제공하지 않는다.
- 캠페인 발송 기능은 별도 승인 Gate 뒤에 추가한다.

## 10. 보안·권한

- `consent` table의 anon/authenticated 직접 insert/update/delete 권한을 철회한다.
- 사용자는 허용된 API를 통해 본인 설정만 변경한다.
- 서버 API는 인증, 계정 상태, same-origin, zod 검증을 매 요청 다시 수행한다.
- 운영센터는 `resolveAdminContext`를 통과한 service-role DAL만 사용한다.
- UI에 전달하는 DTO는 집계값과 마스킹된 참조만 포함한다.
- 계정 병합은 둘 중 더 최근 변경을 보존하되, 병합 중 발송을 멈추고 모든 원장 provenance를 유지한다. 실제 자동 병합 활성화 전 별도 위험 검토를 거친다.

## 11. 기존 데이터 이행

1. 원장에 analytics/marketing 이력이 있으면 최신 원장을 우선한다.
2. 원장이 없으면 `age_and_consent_status` 현재값을 `legacy_backfill` 원장으로 한 번 기록한다.
3. 불일치 건수를 migration 전후로 계산한다.
4. 이행 뒤 current와 latest ledger가 다른 행이 0건이어야 한다.
5. localStorage의 optional 값은 로그인 요청에 재사용하지 않고 제거한다. 필수 동의 draft만 유지할 수 있다.

## 12. 법무 검토 항목

이 문서는 제품·기술 기준이며 법률 자문을 대체하지 않는다. 출시 전 다음을 확인한다.

- 선택 동의를 강요하거나 기본 선택하는 다크패턴이 없는지
- 수집 항목·목적·보관기간·거부 영향 문구
- 광고성 정보 채널별 사전 동의, 수신거부와 정기 확인 의무
- 미성년자와 해외 이용자에 대한 추가 동의 요건

참고한 공식 자료: 개인정보보호위원회의 모바일 앱 다크패턴 점검 안내, 개인정보 처리 동의 원칙 안내, KISA의 불법스팸 방지 안내. 실제 출시 문구는 최신 법령과 법무 검토를 다시 거친다.

## 13. 구현 Gate

### Gate A — 데이터 일관성

- 현재값과 이력이 하나의 transaction에서 바뀐다.
- 기존 true + 새 브라우저 미체크는 true를 유지한다.
- 설정에서 철회한 뒤 stale local 값으로 다시 로그인해도 철회가 유지된다.
- 두 계정이 같은 브라우저를 써도 선택값이 섞이지 않는다.

### Gate B — 소비 지점 차단

- analytics false면 선택 이벤트가 한 건도 저장되지 않는다.
- marketing false, 미인증 연락처, 비활성 계정은 audience에서 제외된다.
- DB 상태 확인 실패는 fail-closed다.

### Gate C — 사용자 경험

- 두 선택의 차이를 로그인 화면에서 이해할 수 있다.
- 두 항목 모두 마이에서 조회·변경·철회할 수 있다.
- 미동의 사용자도 서비스 이용에 차이가 없다.

### Gate D — 운영센터

- 동의율, 대상 수, 최근 변경, 수집 상태가 보인다.
- 원문 연락처와 민감 metadata가 클라이언트 payload에 없다.
- 운영자가 동의를 임의 부여할 수 없다.

### Gate E — 검증

- RPC 원자성·동시 변경·재시도 테스트
- API 인증·CSRF·입력 검증·fail-closed 테스트
- analytics granted/revoked 저장 테스트
- marketing audience 포함·제외 계약 테스트
- DB 권한 회귀 테스트
- 관리자 DTO PII 부재 테스트
- 모바일 320px 이상, 키보드, 스크린리더 상태 안내 점검

## 14. 완료 정의

두 체크박스가 동일한 canonical preference를 사용하고, 서버가 선택형 데이터 수집과 마케팅 대상 계산에서 이를 강제하며, 사용자가 언제든 변경할 수 있고, 운영자가 개인정보 원문 없이 상태를 관리할 수 있을 때 완료로 본다.
